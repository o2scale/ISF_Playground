# Development Workflow Standard

**Last Updated:** October 10, 2025
**Purpose:** Define the standard process for story implementation and QA handoff

---

## 📋 Standard Process

### 1. Story File is the Single Source of Truth

All implementation details, test scenarios, and QA guidance should be documented **directly in the story file** (`docs/stories/sprint5-story-XX-name.md`).

**Do NOT create separate dev agent records** unless absolutely necessary for context continuity across major context breaks.

---

## 2. Story File Structure

### Required Sections:

#### **Header**
```markdown
**Story ID:** Sprint5-Story-XX
**Epic:** Sprint5-Epic-XX
**Sprint:** Sprint 5
**Date Created:** YYYY-MM-DD
**Date Completed:** YYYY-MM-DD (when done)
**Status:** ✅ Ready for QA | 🔄 In Progress | 📝 Draft
**Priority:** P0/P1/P2/P3
**Estimate:** X days
**Actual:** X days (when done)
**Assigned To:** Developer Name
```

#### **Acceptance Criteria** (with Implementation Details)
```markdown
### AC1: Feature Description ✅
**Given** context
**When** action
**Then** expected result

**Implementation:**
- `filename.js:line-range` - What was implemented
- Key functions/components involved
- Important notes for QA
```

#### **Technical Specification** (with Completion Status)
```markdown
### Backend Implementation ✅ COMPLETE

#### API Endpoint
- Actual endpoint URL
- Request/response examples
- Error responses
- File references with line numbers

### Frontend Implementation ✅ COMPLETE
- Components created/modified
- File references with line numbers
- Key functions and their purposes
```

#### **QA Testing Guide**
```markdown
### Test Scenarios

#### ✅ Test 1: Happy Path
1. Step-by-step instructions
2. ...
**Expected Results:**
- What should happen

#### ✅ Test 2: Error Case
...

### API Testing
- Curl/Postman examples
- Authentication requirements

### Database Verification
- Queries to verify data integrity
```

#### **Implementation Files**
```markdown
### Backend
- `path/to/file.js:line-range` - Description

### Frontend
- `path/to/file.jsx:line-range` - Description
```

#### **Definition of Done**
```markdown
- [x] All acceptance criteria met
- [x] Feature implemented
- [ ] Unit tests passing
- [ ] E2E tests passing
- [ ] QA review passed
```

## 3. When to Use Dev Agent Records

**Only create dev agent records (`STORYXX_DEV_AGENT_RECORD.md`) when:**

1. **Context Break During Complex Implementation**
   - Story spans multiple sessions
   - Need to preserve detailed implementation state
   - AI needs to resume complex refactoring

2. **Multi-Developer Handoff**
   - Passing work between developers
   - Need technical implementation notes beyond story scope

3. **Architecture Decisions**
   - Document why certain approaches were chosen
   - Preserve alternatives considered

**Otherwise:** Update the story file directly.

---

## 4. QA Handoff Checklist

Before marking a story as "Ready for QA":

- [ ] All AC marked with ✅
- [ ] Implementation details added to each AC
- [ ] QA Testing Guide section complete with test scenarios
- [ ] API endpoints documented with examples
- [ ] Database verification queries provided
- [ ] Implementation Files section lists all modified files
- [ ] Definition of Done updated
- [ ] Status changed to "✅ Ready for QA"
- [ ] Date Completed added
- [ ] Dev agent record deleted (if one was created)

---

## 5. Benefits of This Approach

### ✅ Advantages:
- Single source of truth for QA
- No duplicate documentation
- Story file always up-to-date
- QA has everything in one place
- Easier to maintain
- Clear handoff process

### ❌ Disadvantages of Dev Records:
- Creates duplicate documentation
- Can become stale/outdated
- QA has to check multiple files
- Extra maintenance overhead
- Easy to forget to update

---

## 6. Example Workflow

### Developer Workflow:

```bash
1. Read story file: docs/stories/sprint5-story-XX.md
2. Implement feature
3. Update story file with:
   - Implementation details in each AC
   - File references with line numbers
   - QA test scenarios
   - API examples
4. Mark story as ✅ Ready for QA
5. Delete any dev agent records created
```

### QA Workflow:

```bash
1. Read story file: docs/stories/sprint5-story-XX.md
2. Review all ✅ AC with implementation details
3. Follow QA Testing Guide
4. Test each scenario
5. Verify database changes
6. Update Definition of Done checklist
7. Report results back in story file or separate QA report
```
